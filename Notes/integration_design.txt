CLIENT AND FS INTEGRATION DESIGN
Updated 2026-10-02.

This is the current shared plan, not a work log.
AGREED describes settled behavior.
PROPOSED describes an approach we can still change.
OPEN describes a decision needed before its dependent implementation.
Detailed implemented formats belong in source headers and Docs.
Record only meaningful decisions, unresolved issues, and deviations; omit routine work logs.


GOAL AND SCOPE
    The client owns encryption and the meaning of social data.
    FS stores opaque blobs and manages access, quotas, and transfers.
    Proxy and P2P carry the same logical operations.
    Remove the DB actor after replacing its remaining responsibilities.
    FS may retain its own local index; ledger internals remain outside this upgrade.
    Each user has one home node, and a node may host many users.
    Support users on the same node and on different nodes.
    Home-node migration and historical-post delivery to new recipients are deferred.
    No deployed compatibility or data migration is required.
    Do not erase existing development data without a separate request.


CURRENT IMPLEMENTATION
    Core client initialization, cleanup, pooled buffers, and blob assembly are implemented.
    Signing uses Ed25519; pairwise encryption uses supported Ed25519-to-X25519 conversion.
    Login sends one username request and unlocks the returned encrypted account header locally.
    Account request and response metadata codecs are shared in common.
    parse_request handles account retrieval and blob get/put/delete request headers.
    Shared blob locators and mutation signature helpers are implemented.
    Ciphertext upload framing, commit handling, and client/node blob operations remain unfinished.
    Legacy post requests and the disabled post-feed response slot are removed.
    Feed-page storage/codecs and incremental package parsing/marshaling are implemented.
    Feed navigation is declared but awaits loading and scheduling decisions.
    Package retrieval connects blob assembly, encrypted framing, and staged package parsing.
    Node username resolution, blob request handlers, and client/node integration remain unfinished.
    The old common owner-update codec still uses identifier/index locators and needs reconciliation.
    Focused tests do not establish a complete application build or working end-to-end integration.


AGREED: REQUESTS AND BLOB AUTHORITY
    Account retrieval by username is the pre-login special case.
    All other content uses blob retrieval, insertion, and deletion.
    Feeds, packages, voucher lists, and permission lists need no separate content request types.
    Every request starts with version:u16 and RequestKind:u16, both big-endian.
    Dispatch through one parser, not paths.
    Blob locator = H(request_hash || namespace_public_key).
    Retrieval supplies the namespace public key without requiring a client signature.
    Insertion signs H(request_hash || operation || ciphertext_hash).
    Deletion signs H(request_hash || operation).
    Encode operation as the request kind's big-endian u16, not its native enum representation.
    Verify that signature under the namespace public key before mutation.
    Before committing an insertion, verify the uploaded ciphertext matches its signed hash.
    Whole-ciphertext hashing remains separate from locator derivation.
    This replaces the older identifier/index locator and complete-frame blob-signature proposals.
    Request kinds are account=1, blob get=2, blob put=3, and blob delete=4.
    Blob requests contain owner key and label; mutations add a signature, and put adds ciphertext hash.
    These headers do not define how ciphertext chunks are uploaded or finalized.


AGREED: HOST BOUNDARY AND OWNERSHIP
    The host implements send_request and supplies responses through client_parse_response.
    send_request is asynchronous and may retain an outgoing buffer for an arbitrary duration.
    Build requests in client-owned networking buffers and encrypt in the same allocation.
    The host receives the original buffer descriptor from the context send-buffer array.
    Neither returning from send_request nor receiving a response releases that buffer.
    Only client_return_buffer allows reuse.
    Cancellation and completion reserve the context while the host holds its buffer.
    Return all outstanding buffers before destroying the client.
    Incoming buffers are borrowed only during parsing; copy anything retained.
    Validate untrusted bytes at the boundary instead of repeating checks inside every helper.
    Allocation and capacity management belong to the buffer owner.
    Current response handlers expect complete protocol messages/chunks.
    Arbitrary fragmented or coalesced transport input still needs outer framing.
    The native inline socket sender still needs a host-owned queue and partial-write handling.


AGREED: ACCOUNT AND KEYS
    The username request returns account identity, ciphertext hash/size, then encrypted header chunks.
    No second client hash-fetch request is required.
    Passwords and secret keys never go to the node.
    Derive the unlock key locally using the envelope's bounded Argon2id parameters.
    The implemented profile is Argon2id 1.3, two passes, and 64 MiB with a fresh salt.
    Authenticated decryption and format validation must succeed before installing account state.
    Bind the recovered signing identity to the returned account public key.
    One password-encrypted account header contains signing seed, data_key, page indices, and inbox locator.
    Its plaintext is 132 bytes; the current password envelope is 213 bytes.
    The password-derived key protects this header, not the other content.
    data_key protects owner-managed pages and private metadata, including retained package keys.
    Changing a password re-encrypts the header while preserving signing identity and data_key.
    Local credential storage, registration, recovery, and password-change publication remain unfinished.


AGREED: FEEDS AND PACKAGES
    A feed contains loaded FeedPages and tracks the current page number.
    Each page contains packed fixed-size post metadata.
    A post stores originator, creation time, package hash, package key, and blob count.
    Append while the page has room; on fullness, increment the page number and start a new page.
    Do not pad the new page with empty slots.
    A plaintext feed page is at most 64 KiB, including its header.
    Reject page-index overflow and leave a full page unchanged on failed append.
    One post package contains the post-data blob first, followed by its enclosed blobs.
    The first blob's text and attachment-reference format remains open.
    Package plaintext is version:u16, count:u32, all sizes:u64, then all payloads in order.
    Framing integers are big-endian; there are no individual blob hashes in the size table.
    Package owns one plaintext payload buffer and its descriptor array.
    Each descriptor contains size and a borrowed pointer into that shared buffer.
    Eviction and destruction release the complete package, not individual enclosed blobs.
    Parse successive slices into staging storage and copy borrowed bytes before returning.
    Keep staging separate from live contents until parsing and authentication complete.
    marshal_package fills caller-owned output chunks without allocation.
    Retain the original encrypted package and its key when storing received posts.
    Package retrieval preserves ciphertext in the blob cache and replaces its destination only on success.
    Its caller keeps the destination alive and at a stable address until completion or cancellation.
    Feed retrieval and broader client-state integration remain unfinished.


ENCRYPTION AND TRANSFER CHUNKS
    Hash the complete stored ciphertext, never just the current transfer chunk.
    Existing first transfer chunk: whole-blob hash, native uint64_t total size, then payload.
    Existing continuation: whole-blob hash, then payload.
    Existing assembly uses the pool when the blob fits its largest bucket, otherwise heap storage.
    The complete blob hash is verified after assembly.
    Transport chunks and authenticated encrypted chunks are separate boundaries.
    Stored envelope: version:u16=1, suite:u16=1, and a 24-byte secretstream header.
    Follow with ciphertext_length:u32 and ciphertext for each encrypted chunk.
    Use a fresh secretstream for each blob and at most 64 KiB plaintext per encrypted chunk.
    Reserve the extra 17 authentication bytes in the networking allocation.
    Bind the envelope and chunk ordinal as authenticated additional data.
    Require a final tag; reject truncation, invalid tags, and trailing data.
    A transport may split an encrypted chunk across messages.
    Node transfer memory must stay bounded for content larger than its networking buffers.
    The client framing codec encrypts/decrypts complete chunks in caller-owned buffers.
    The caller derives final from the declared whole-blob size; the codec verifies the final tag.
    The incremental encrypted reader assembles split fields/chunks in caller-owned scratch storage.
    Package operations use the incremental reader; feed loading and upload finalization remain open.


PERMISSIONS AND VOUCHERS
    Register batches of permission hashes and publish batches of voucher hashes in FS state.
    Shared requests support permission registration, permission revocation, and voucher publication.
    Each batch carries the owner key, count, hashes, and a signature covering the request.
    Voucher publication carries one UTC expiry in seconds for the whole batch.
    TODO: adapt node handlers and FS voucher state to this batch expiry when integrating these requests.
    The client's private permission list remains an ordinary encrypted blob.
    The remote presents the plaintext record when using a permission or voucher.
    The local node hashes that record and checks its registered hashes; registration needs no record lookup.
    AGREED: permissions record recipient consent to incoming voucher delivery.
    Sender publication and voucher issuance record sender consent to transfer.
    A voucher offers later retrieval of one complete prepared package.
    Its node-readable part identifies issuer, recipient, package hash, size, and permission.
    Its encrypted subsection contains the package key, encrypted with the recipient's shared key.
    Use a fresh nonce for each encrypted key subsection.
    The sender signature binds both portions; the node never needs the package key.
    Recipient feed metadata retains the recovered key under the recipient's data_key.
    Removing permission stops future deliveries and cancels outstanding vouchers under it.
    Owner deletion cancels vouchers requiring that data but does not erase retained recipient copies.
    OPEN: reconcile unsigned blob retrieval with voucher authorization and resource limits.
    PROPOSED: keep issued-voucher state and paged recipient inboxes in the node's durable index.
    Admit an inbox entry only after permission and sender-signature checks.
    Duplicate delivery must not append the same voucher twice.
    Revocation stops admission locally and must remain pending for delivery to an unreachable remote node.
    Define canonical permission/voucher encoding before replacing existing native-layout codecs.


PROPOSED: PUBLICATION AND REDEMPTION
    Build and encrypt the package before publishing its feed reference.
    Stage bounded uploads and verify exact hashes and lengths before making references visible.
    Commit the local feed update, issued vouchers, and pending notifications together.
    Include an account-header update when advancing to a new page requires it.
    Notification delivery is separate from publication and can be retried explicitly.
    No atomic transaction spans two home nodes.
    Finalize durable files before publishing references in the local index.
    Record enough state to recover abandoned staging and lost replies after restart.
    Permit only one active attempt per voucher.
    One-time redemption means completed retrieval, not merely starting a transfer.
    Proposed states: Issued -> Transferring -> AwaitingConfirmation -> Redeemed.
    Failure releases reservations and permits an explicit retry unless expired or canceled.
    Completion means durable receipt of the complete verified ciphertext, not client rendering.
    Persist receipts and terminal results so lost replies do not force another download.
    Revocation and deletion cancel affected attempts; already delivered bytes cannot be recalled.
    Same-node transfers use the same validators and ownership rules.
    They still consume recipient logical quota and the voucher, even without physical file duplication.


PROPOSED: LIMITS AND CLEANUP
    Configure per-user disk, metadata, inbox, recipient, and transfer limits.
    Reserve space for partial uploads and incoming transfers before accepting bytes.
    Full quota rejects new writes; users explicitly remove data to make room.
    Automatic node eviction is deferred.
    Earlier suggested defaults: eight active transfers and 4,096 pending vouchers per user.
    Earlier suggested publication limit: 1,024 recipients, supplied in bounded batches.
    Earlier suggested timeouts: 60 seconds idle, 30 minutes per attempt, five minutes for receipt confirmation.
    Use monotonic time for process deadlines and UTC time for voucher expiry.
    Preserve replay protection when expiring result records or deleting objects.
    If physical files are shared, delete only after all ownership and reader references are gone.
    One user's deletion must not remove another user's retained copy.
    These limits and state transitions still need implementation review.

    How does unsigned retrieval preserve permission/voucher policy and prevent resource abuse?
    What are insertion chunk framing, expected size, commit, cancellation, and finalization rules?
    How do mutations handle replay, concurrent replacement, and recreation after deletion?
    Which old owner-update revision rules remain useful under generic blob operations?
    What are username normalization, uniqueness, registration, recovery, and home-node lookup rules?
    What is the first package blob's text and attachment-reference format?
    How does a voucher provide initial package metadata and the correct owner-scoped locator?
    How does Feed report missing pages and schedule their retrieval?
    How are node-managed inbox updates expressed through generic blob operations?
