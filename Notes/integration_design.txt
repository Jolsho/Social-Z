PUBLISHING A POST

    AGREED:
        Store and verify all post blobs before publishing the feed update.
        The feed update is the publication point on Alice's node.
        Notification delivery to other nodes is a separate operation.
        Failed notification delivery can be retried.
        There is no atomic transaction spanning Alice's and Bob's nodes.

    PROPOSED STEPS:
        1. Alice's client reads its header, current page, and recipients.
        2. It creates and encrypts one package; its hash and key are retained in the post metadata.
        3. It creates the replacement feed page and recipient-specific vouchers.
        4. FS opens a bounded upload transaction and reserves Alice's disk quota.
        5. The client uploads ciphertext in chunks to temporary files.
        6. FS checks exact lengths and hashes before accepting staged files.
        7. FS commits the feed update, issued vouchers, and pending deliveries together.
        8. If a page boundary is crossed, the account-header update commits with it.
        9. Alice's node delivers vouchers with Bob's permission.
        10. Bob's node persists each accepted inbox entry before acknowledging delivery.

    PROPOSED FAILURE RULES:
        Each publish attempt has a stable transaction ID.
        Repeating a committed transaction returns its recorded result.
        Reusing the same ID with different contents is rejected.
        A revision conflict leaves the existing feed unchanged.
        Staged uploads may expire or be explicitly aborted.
        Failed voucher deliveries remain listed for an explicit retry.
        No background retry loop is required for the first version.

    PROPOSED DISK COMMIT:
        Files and LMDB are not one atomic transaction.
        Finalize and make the verified files durable before publishing references.
        Commit references, quota accounting, and voucher state in an LMDB transaction.
        Record transaction state so restart recovery can identify leftovers.
        A crash may leave unreferenced files to clean up.
        It must not publish a reference to a missing or incomplete file.


REDEEMING A POST

    AGREED:
        Only one attempt may be active for a particular voucher.
        A failed attempt returns an error and allows an explicit retry.
        One-time use means a completed retrieval, not merely starting a transfer.
        Both same-node and different-node retrieval obey these rules.

    PROPOSED STEPS:
        1. Bob's client reads its inbox and selects a voucher.
        2. Bob authorizes his home node to redeem it.
        3. Alice's node verifies signature, recipient authority, expiry, and issued state.
           It also rejects vouchers canceled by revocation or owner deletion.
        4. It checks that the bounded manifest still names available blobs.
        5. Bob's node reserves space for the complete post.
        6. Alice's node streams the manifest's ciphertext blobs in one transfer.
        7. Bob's node verifies each hash and length and commits the received files.
        8. Bob's node confirms durable receipt to Alice's node.
        9. Alice's node records the voucher as redeemed.
        10. Bob's client decrypts the key envelope, post header, and media.
        11. The client parses authenticated plaintext and presents the post.

    PROPOSED STATE MACHINE:
        Issued -> Transferring -> AwaitingConfirmation -> Redeemed.
        Failure before confirmed receipt returns to Issued after releasing the session.
        Expired vouchers cannot start new attempts.
        Redeemed and expired outcomes survive restart.
        Canceled outcomes also survive restart and cannot be reopened by retries.
        Repeated confirmations return the same result.
        A lost confirmation reply must not force another complete download.
        Use a transfer ID and authenticated completion receipt to resolve that case.
        Unfinished sessions have deadlines and release their quota reservations.
        Retries may restart from the first blob initially.
        Resuming arbitrary byte offsets can be a later feature.
        One-time redemption does not promise exactly one transmission of every byte.
        Failed attempts may have sent partial data.
        Revocation or owner deletion transitions affected vouchers to Canceled.
        Cancellation releases sessions and quota reservations when processed.
        It does not erase bytes already delivered to Bob.

    PROPOSED CONFIRMATION MEANING:
        Completion means Bob's node has stored the complete verified ciphertext.
        Alice's node does not wait for Bob to render the post.
        Client decryption errors remain visible even after ciphertext storage succeeds.
        Expiry and receipt races need explicit tests.

        A session timeout before confirmed completion releases the attempt.
        Retries use a new transfer ID and remain subject to expiry and cancellation.
        Persist receiver receipt records before sending them.
        Retain issuer transfer metadata long enough to verify a late, valid receipt.
        A late receipt must still fall within its original confirmation window.
        If a retry has started, a valid prior receipt completes the voucher and stops that retry.
        Restart releases unfinished attempts and reconciles verified receiver files.
        Terminal outcomes are never reopened by retries.

    REVOCATION AND DELETION:
        Bob's node immediately blocks delivery and local redemption after revocation.
        Alice's node cancels outstanding vouchers when it processes Bob's signed revocation.
        This first version uses durable propagation rather than a distributed atomic revoke.
        Offline remote nodes may temporarily retain old permission knowledge.

        Session, disk, metadata, inbox, and recipient limits are configured per user.

        A full inbox returns quota failure and leaves delivery pending at Alice.

    ACCEPTANCE TRACE:
        Alice publishes post P and commits its feed page plus vouchers VA and VB.
        Bob A accepts VA through a valid permission.
        Bob B's inbox is full, so VB stays pending at Alice.
        Bob A retrieves all ciphertext in bounded chunks and persists a receipt.
        Alice commits VA as Redeemed.
        The receipt reply is lost.
        Bob A resends the receipt and receives the same completed outcome.
        Alice explicitly retries VB after Bob B makes space.
        Bob B revokes the permission before redemption.
        His node blocks locally and propagates the signed revocation.
        Alice cancels VB when the revocation arrives.
        A subsequent VB redemption returns Canceled without allocating a file transfer.
        Repeat the same trace with Alice and both Bobs on one home node.
